何を、何のために
Cloud Run に
移設しようとしたか

会社の事業

  • スマホアプリ開発・運用のためのプラットフォームを提供
  • 導入アプリ数は数百、積み上げMAUは1億超

データ基盤概略図

BigQueryを中心に置き、多数のデータ入出力経路が存在

データ基盤の管理APIs

  • 各経路の内部向け/外部向けに、データ入出力用/管理用のWeb APIが存在
  • 普段はほとんどリクエストがないが、急に並列リクエストが来る
    • お客様からのデータインポート・エクスポートリクエスト
    • 定時バッチからの利用
  • 最大負荷を捌ける数+1台のGCE(VM)のクラスタを常時稼働
  • Python + Flask + Gunicorn または Python + FastAPI + uvicorn で実装
  • Dockerコンテナとしてデプロイ

管理APIの課題

コスト

小さなクラスタのコストが積み重なって高コストになっていた
  • APIの数が多い => クラスタの数が多い
  • 環境の数が多い
    • 開発環境
    • ステージング環境
    • お客様向けサンドボックス環境 (社内としては商用環境の扱い)
    • 本番環境

運用

OSのセキュリティ更新・EOLの管理が面倒

課題の解決策

サーバレス基盤に移設しよう

  • 起動・スケーリングの速さを活かし、普段はコンテナを0台にして、
    リクエストに応じてスケールさせればコスト問題は解決
  • OS管理も不要になる
  • 過去に常駐Airflowのバッチ基盤を Workflows + Cloud Run Functions で置換し、
    コスト・性能・運用性を大幅に改善    した成功体験がある
  • スケーリング速度に優れ既存Docker Imageの流用が可能な Cloud Run を選択

移設時に発生した問題と解決策

Cloud Run に移設した結果

  • 移設自体は簡単だった
    • Docker Imageのデプロイ先を変えるだけ
  • 機能テストも全く問題なく通った
  • しかし、運用テストではエラーが多発
    • The request was aborted because there was no available instance
      による429,500エラー
    • Gunicornの
      [CRITICAL] WORKER TIMEOUT
      [ERROR] Worker was sent SIGKILL! Perhaps out of memory?

The request was aborted because there was no available instance

429, 500エラーの原因

  • インスタンスが無いと言われている
    • 十分な最大インスタンス数を指定したはずなのに
  • 公式ドキュメントで原因の候補に挙げられているのは
    • トラフィックが急増している。
    • コールド スタート時間が長い。
    • リクエスト処理時間が長い、またはリクエスト処理時間が急増している。
    • サービスがコンテナ インスタンスの上限（HTTP 429）に達した。
    • Cloud Run サービスに起因する一時的な要因。
  • 「コールド スタート時間が長い」が原因?
    • VM時代は常時稼働前提だったので、コンテナ起動時間は考慮されていなかった

VM時代のDockerfile

パッケージ管理に利用していたPoetryが、起動時間の悪化を招いていた 
    
FROM python3-slim

WORKDIR /var/www
COPY src /var/www
# Python標準のpipではなく、Poetryでパッケージを管理していた
# Poetryと依存ライブラリが70MB以上のストレージを消費
RUN pip install poetry
# Poetryは、デフォルト設定では依存ライブラリをインストールする時にvirtualenvを自動作成する
# virtualenvが15MB以上のストレージを消費
RUN poetry install
# poetry run アプリケーションでは、Pythonが2重起動する
# 1. Pythonが起動してPoetryをロードし、Poetryがアプリケーション起動コマンドを組み立て
# 2. Poetryが起動コマンドを実行し、Pythonアプリケーションが起動
ENTRYPOINT ["poetry", "run", "gunicorn"]
CMD ["--config", "/var/www/gunicorn_settings.py"]

Cloud Run 向けのDockerfile

Poetryによるパッケージ管理は維持しつつ、イメージサイズを縮小し起動コマンドを短縮 
    
FROM python3-slim AS builder

WORKDIR /var/www
COPY src /var/www
RUN pip install poetry poetry-plugin-export
# 依存ライブラリをPoetryからpip用の形式でエクスポート
RUN poetry export -f requirements.txt -o /var/www/requirements.txt

# デプロイ用イメージにはPoetryをインストールしない
FROM python3-slim

WORKDIR /var/www
COPY src /var/www
COPY --from=builder /var/www/requirements.txt /var/www/requirements.txt
# 隔離されたコンテナの中なので、さらにvirtualenvで環境を隔離する必要はない
RUN pip install --no-cache-dir --require-hashes -r requirements.txt
# アプリケーション起動コマンドを直接実行
ENTRYPOINT ["gunicorn"]
CMD ["--config", "/var/www/gunicorn_settings.py"]

コールドスタート時間短縮の結果

効果はアプリケーションにより異なるが、下記の例では 約3.5秒 => 約0.8秒

エラーの頻度は減少したものの、完全解消には至らなかった

429, 500エラーの原因(2)

  • インスタンスが無いと言われている
    • 十分な最大インスタンス数を指定したはずなのに
    • 起動時間が長過ぎる問題は解消したはずなのに
  • ドキュメントによると、インスタンスのCPU使用率が高い場合、
    そのインスタンスにはリクエストを割り当てない
    • 起動直後のインスタンスはコンテナ起動のCPU負荷で高負荷と判断され、
      さらに次のインスタンス起動が必要と判定される?

インスタンス不足解消: 最大インスタンス数を大きく設定する

  • 最大インスタンス数をかなり大きめに設定してみた
  • 429, 500エラーは解消した
  • 起動負荷が次のインスタンス起動を招く状況への対処が必要らしい
  • 実際に、インスタンスはリクエスト開始直後に多めに起動し、すぐに減るような挙動
  • 最大インスタンス数を大きめに設定しても、
    不要になったインスタンスはすぐに開放されるので、高額課金の心配はない

Gunicornの WORKER TIMEOUT, SIGKILL

Gunicronのエラー原因

ソースコードの該当箇所を確認すると、Gunicornのワーカー死活監視は
「バックグラウンドアクティビティ」相当の実装
バックグラウンドアクティビティは、リクエスト時のみCPUを割り当てる場合は回避すべきとされている

Gunicornのエラー原因

リクエスト時のみCPUを割り当てる設定のCloud Runで動作させた場合に
リクエスト間隔が空くと、正常稼働中のワーカーがタイムアウトしたと誤認されてしまう

  1. リクエストがなくなる
  2. インスタンスへのCPU割当がなくなり、ワーカーの時刻更新とワーカー監視のループが停止
  3. リクエストが発生
  4. インスタンスにCPUが割り当てられ、ワーカーの時刻更新とワーカー監視のループが再開
  5. ワーカー監視が先に実行された場合、全ワーカーの最終更新時刻はCPU割当停止前の時刻
  6. マスターは全ワーカーがタイムアウトしたと誤認
  7. マスターは全ワーカーをkillし、新たなワーカーを起動

Gunicornのタイムアウト誤認の影響

ワーカーが誤ってkillされることで、2つの問題が発生

応答遅延

  • 一時的にワーカー数が0になり、ワーカー起動までリクエストが待たされ、応答が遅延する
  • 確実に発生

応答失敗

  • リクエストを受け付けたワーカーが応答を返す前にkillされる
  • 運が悪いと発生

Gunicornのタイムアウト誤認解消方法

  • リクエストタイムアウトを0(無制限)に設定すれば解消する(した)
    • リクエストタイムアウトのチェックが行われなくなるため
  • 実際、Cloud Run 公式のgunicorn利用ガイドでは(説明なく)timeoutを0に設定している
  • しかし、リクエストタイムアウトのチェックを止めると
    本当にハングアップしたワーカーを排除できなくなってしまう

Gunicorn timeout=0 の場合のワーカー死活監視

  • Cloud Run のヘルスチェック設定を、特定のエンドポイントへのHTTPリクエストに変更する
    • デフォルトではTCPのポート確認
    • ライブネスプローブで設定変更できる
    • アプリケーションがハングアップして応答できなくなった場合は、
      コンテナインスタンスごと入れ替わる
  • Cloud Runのリクエストタイムアウトは
    "コンテナからの応答を待つのを止めてエラーを返す"
    であり、コンテナ内の処理は止まらない
    • コンテナ内で無限待機・無限ループのような状態が発生すると、
      偶然コンテナが入れ替わるまで、その処理は残り続ける(実験済)

VM から Cloud Run に移行する時に考慮が必要な点のまとめ

  • コンテナ起動時間を短縮する
    • イメージサイズの縮小
    • 起動処理の短縮
    • 常時起動前提では、コンテナ起動時間に意識が向いていないことがある
  • 最大インスタンス数は多めに設定する
    • インスタンス起動負荷が次のインスタンス起動を呼ぶので、
      起動の瞬間は多数のインスタンスが必要になることがある
  • バックグラウンドループがないか確認する
    • CPUの割当剥奪・再開が誤動作の原因になり得る
    • 自身が実装した処理だけでなく、ミドルウェア・ライブラリも要確認
  • ヘルスチェックエンドポイントを使用したライブネスプローブを設定する

ノウハウが確立した?

VM上のアプリケーションをCloud Runに移設する方法が分かった
これで全てのアプリをCloud Runに移設でき...てはいない

未解決の課題

  • Cloud Run では、HTTP/1 ではリクエスト・レスポンスともにサイズ制限がある
    • リクエスト: 上限32MiB
    • レスポンス: Transfer-Encoding: chunkedまたは
      ストリーミング メカニズムを使用しない場合は 32 MiB
  • HTTP/2 ではサイズ制限はない
  • 弊社には HTTP/1 で大きなリクエスト・レスポンスを扱うAPIが存在する

検討中の対応策

  • HTTP/2対応のWSGIサーバに変更する
    • Gunicornは現時点でHTTP/2サポートはベータ扱い
    • ベータ機能を本番導入する? 正式にHTTP/2をサポートする製品を探す?
  • NginxでHTTP/2リクエストを受け、HTTP/1に変換してアプリにリクエストを転送
    • Cloud Run ではサイドカーコンテナを使えるので可能なはず
    • せっかくサーバレス化するのにNginxの面倒見るの?
  • データをGCSに置き、署名付きURLを発行する
    • ドメインがstorage.googleapis.comになるのは、
      ドメインごとに通信許可設定をしているお客様に許容されるか?
    • GCSの前段にCloud CDNを置けば、カスタムドメインも実現できるかも?

検討状況

  • 他の開発・運用で手一杯になり、検討は止まっている
  • とりあえず、Cloud Run への移設には何かしらの改修が必要なことは分かった
  • おすすめの方法があれば教えてください

VPC Direct Egress

  • App Engine (Standard) と Cloud Run はどちらもVPC外のサービス
  • 従来は、VPC内の Cloud SQL や Memory Store にアクセスするには
    サーバレス VPC アクセス コネクタ が必要だった
  • Cloud Run では、インスタンスがVPCの内部IPアドレスを持ち
    直接VPC内のリソースに接続できる VPC Direct 下りを利用可能
  • App Engine (Standard) では、VPC Direct 下り はまだプレビュー段階

サーバレス VPC アクセス コネクタ

  • 実態は常時起動のVMクラスタ
    • 実際の利用有無に関わらず常にVM料金が発生する
  • 負荷が増えると、設定された最大台数まで自動的に増える
  • 一度増えた台数は減らない
  • 時々メンテナンスで一時的な通信遅延・通信断が発生する
    • おそらく2週に1度くらいのペースでメンテナンスしている

VPCに直接接続する選択肢を取れるなら、直接接続する方が良い
既存の App Engine 上のWebアプリケーションも、Cloud Run への移設を検討中
